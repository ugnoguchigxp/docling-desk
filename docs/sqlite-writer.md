# SQLiteの書き込みプロセス

画面、Wiki同期、翻訳バッチ、説明用検索索引、バックアップ、復元、DB移行は、`docling_desk.sqlite_writer.connect` を使用する。SQLiteへの直接接続はWriter内部に限定する。バッチの実行プロセスからもDBへ直接書き込まない。

最初の接続時に専用Writerを自動起動する。同じホスト・OSユーザー・プロセス名前空間のクライアントは、保存先やWikiワークスペース、Pythonのインストール場所が異なっても同じWriterに接続する。起動時とプロセスの生存期間をファイルロックで保護し、Writerの重複起動を防ぐ。接続がすべて閉じられて30秒経過すると自動終了する。

通信には、ユーザー専用ディレクトリ `/tmp/docling-desk-writer-<uid>-v1/` のUnixソケットとJSONを使用する。追加サービスの設定や依存パッケージは不要。対応環境は既存のファイルロックと同じmacOS/Linux。同じDBを複数ユーザーや別コンテナのWriterで共有しない。

Writerは書き込み要求を直列に実行する。`BEGIN` や暗黙のトランザクション開始から `COMMIT` / `ROLLBACK` まで書き込み権を保持するため、別クライアントの要求が途中に割り込まない。長時間の翻訳・モデル呼び出しは、これまでどおりDBトランザクションの外で実行する。`mode=ro` の接続は書き込みの待ち列を通らず、SQLiteの読み取り専用制約で保護する。

クライアントの切断・強制終了時は、その接続の未確定変更をロールバックする。Writerが停止した場合、接続済みの処理はエラーになり、次の新規接続でWriterを再起動する。通信が切れた要求は自動再送しない。コミットが完了して応答だけ失われた可能性があるため、保存状態を確認してから再実行する。

`Store.connection()` は既存のトランザクション範囲を保つ。読み取りだけの用途は `Store.connection(readonly=True)` を使用できる。`BatchStore.db` の明示的な `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` も同じWriter内で実行される。現在の接続APIは、このプロジェクトが使用する `execute`、`executemany`、`executescript`、行参照、コミット、ロールバック、ファイルDBのバックアップを扱う。

独立したKnowledge APIは別の保存領域を持ち、そのAPIプロセスがWriterを担う。`knowledge-api/src/writer.ts` がDBごとに生存期間全体のロックを取得し、別プロセスはスキーマ初期化より前に拒否する。既存の期限付きワーカーリースが失効しても、稼働中プロセスから書き込み権を奪えない。同一プロセス内の複数Storeはロックを共有する。`<DB名>.writer-lock` はSQLiteのOSロックを利用する調整用ファイルで、プロセス終了時にロックが解除される。稼働中にこのファイルを削除しない。

回帰テストは `tests/test_sqlite_writer.py` と `knowledge-api/tests/writer.test.ts` にある。複数プロセスの更新、UIとバッチのWriter共有、途中終了のロールバック、Writer停止からの復旧、ロック待機期限、読み取り専用接続、バックアップ、外部APIのプロセス所有権を確認する。
