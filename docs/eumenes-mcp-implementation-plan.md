# Eumenes向けMCP拡張とツール利用ガイドAPIの実装計画

Docling DeskをEumenesから利用し、資料の取り込み、検索、根拠の確認、原本閲覧、Markdownの編集と保存を一連の操作として行えるようにする。既存MCPを拡張するとともに、ツールの前提条件、操作順序、入出力例、失敗時の対処を必要なときに取得できる利用ガイドAPIを追加する。

作成日：2026年10月16日。状態：利用ガイドAPIとMCP取得、P3の文書操作を実装済み。対象コミット：`103d38a9ad4cb893b7ae60e9f3df4e486a370691`を基準とする作業ツリー。未実装のAPI名・追加項目は予定契約であり、各段階の開始時に既存契約と照合して確定する。

## 1 目的と完了条件

EumenesのLLMが利用ガイドを読み、必要な操作を選び、取得したID・版・処理状態を使って次の操作へ進められることを目指す。判断と文章生成はEumenesが担当し、Docling Deskは取得、変換、保存、状態管理、契約検証、認可を担当する。

初期実装の完了条件は次のとおり。

1. HTTPとMCPのどちらからも、利用ガイドの一覧・全体説明・ツール別説明・作業手順を取得できる。
2. 既存の検索、根拠取得、閲覧、下書き、編集、添付、ジョブ操作にガイドが対応し、追加操作にも同じ規約を適用する。
3. PDF・Office・Markdownを取り込み、処理状態を確認し、検索と根拠取得、指定範囲・表・画像の取得へ進める。
4. 根拠を確認した結果をMarkdown下書きへ保存し、編集・確定・検索反映の状態を区別できる。
5. 誤った版、重複送信、通信断、権限不足、未設定機能について、ガイドと実際の応答が一致する。
6. 文書や検索結果に含まれる命令文を、サーバー管理の利用ガイドとして扱わない。
7. 隔離したHTTP・MCP結合試験と通し試験が成功し、実Eumenesでの接続結果を別に記録する。実Eumenesが利用できない場合、そこまでを完了扱いにしない。

## 2 対象と保存先の境界

基本接続は既存の独立ナレッジAPIとgatewayを使用する。[外部文書基盤の既存計画](external-document-platform-implementation-plan.md)と[現在の接続手順](external-document-platform.md)を引き継ぎ、すでに実装された編集・添付機能を作り直さない。

| 接続先 | 今回の位置付け | 保存先と認可 |
| --- | --- | --- |
| 独立ナレッジAPI | 初期実装の必須範囲 | 既存SQLite・原本領域。Bearer、actor、actions、collection・project・regionを維持 |
| MCPと閲覧gateway | MCP・ガイドHTTP API・閲覧仲介の入口 | 資格情報と利用者の対応を管理。DBや原本への直接保存はしない |
| デスクトップ資料・Wiki | 第2段階の拡張範囲 | 既存`data/`と共通処理を使う。独立APIへの複製や暗黙の移行はしない |
| Eumenes | 接続契約と受入手順を提供 | 利用者認証、MCP接続、ファイル受け渡し、画像入力、会話と成果物の表示 |

デスクトップ画面と同じ資料へのアクセスは第2段階で扱う。初期実装の接続だけで、既存デスクトップ資料やWikiが検索・編集できるとは案内しない。接続先の種類を機能情報と全体ガイドに明記する。

製品コードの実装時も、Eumenes本体の変更、本番配備、既存資料の移行、ブログ等への外部公開、DB統合、認証基盤の刷新は対象外とする。任意のシェル、SQL、ファイルパス、URL転送を実行する汎用ツールは追加しない。新しい依存は契約上必要な場合に限定し、MCP SDKやプロトコル版の更新を本機能の前提にしない。

## 4 公開する操作

### 初期実装の必須操作

以下は操作群であり、一つのツールに任意のactionを詰め込む指定ではない。既存名を維持し、追加名だけをP0で確定する。

| 操作群 | ツール名 | 変更 |
| --- | --- | --- |
| ガイド閲覧 | `list_tool_guides`、`get_tool_guide` | 新設。全体説明、各ツール、作業手順を取得 |
| 利用範囲と機能 | 既存`list_document_scopes`、追加`get_document_capabilities` | 接続先の種類、提供操作、形式、上限、OCR・意味検索・画像取得の設定と稼働状態を明示 |
| 一覧と文書 | 既存`list_documents`、`get_document`、追加`get_document_status` | 原文と抽出本文の違いを維持。現在版、文書ETag、FTS・意味索引・処理状態を取得 |
| 検索と根拠 | 既存`search_documents`、`get_document_context` | 既存契約を使用。ガイドでretrievalと版の引き継ぎを説明 |
| 構造と範囲 | `get_document_outline`、`get_document_section` | 既存の抽出結果・要素参照を使い、節やページ等を範囲指定で取得 |
| 表 | `list_document_tables`、`get_document_table` | 表ID、見出し、セル構造、出典を取得。必要に応じCSVを返す |
| 画像 | `get_document_page_image` | ページ・スライドの既存描画を認可経由で取得。画像内容をMCPの画像として返す |
| 原本閲覧 | 既存`request_document_view`、`connect_document_view` | バージョン付き参照と既存接続承認を使用 |
| 取り込みと改版 | `import_document`、`replace_document_source` | 既存multipart APIへ接続。受け渡し方式は第7節で確定 |
| Markdown編集 | 既存の作成、メタデータ、下書き一覧・作成・取得・全文更新・部分編集・確定 | 新設せずガイドを整備。原文、UTF-8範囲、ETag、再送キーを説明 |
| 添付 | 既存の登録・一覧・取得ツール | 文書・下書きへの所属、版、取得上限を説明 |
| 処理と復旧 | 既存`get_document_job`、`retry_document_job`、`get_document_operation`、追加`reextract_document`、`reindex_document` | 既存HTTPの再抽出・再索引を公開。応答喪失後の結果照会を案内 |

一括取得は件数・応答量を制限し、続きの取得方法を返す。範囲の単位は抽出形式に従う。PDFのページ、PPTXのスライド、XLSXのシート番号は既存参照に合わせて1始まりとし、Word等に存在しないページ番号を推測で付けない。部分編集のUTF-8バイト範囲は既存どおり0始まりの半開区間とする。

### 第2段階の拡張操作

デスクトップ資料の一覧・検索・取り込み・原本取得、フォルダー作成・名前変更・移動・コピー、Wikiの記事取得・取り込み・更新、保存済み翻訳・解説の取得と生成、削除を対象候補とする。

この段階は初期実装の完了条件に含めず、接続先の選択と認可対応を確定してから着手する。認証のないローカルHTTPルートをそのまま遠隔公開しない。独立API用UUIDとデスクトップ用IDを混同しない接続単位の参照を定め、モデル引数で利用者や権限を作らない。

削除は対象・現在版・保持と物理削除の範囲を取得できる専用操作にする。既存APIの契約を超える一括削除は追加しない。翻訳・解説の既存処理は、外部送信設定・再実行・課金の扱いを確定した上で接続する。

## 5 ツール利用ガイドの契約

### Descriptionとガイドの役割

Descriptionには、何を行うか、主な前提、関連するガイドIDを短く記載する。詳細な操作順序や復旧方法はガイドで提供する。全体説明を全ツールへ貼り付けず、Eumenesが必要な説明だけ取得できるようにする。

`list_tool_guides`と`get_tool_guide`のDescriptionには、その2ツールだけで全体説明へ到達できる最小の呼び出し例を含める。初回接続では`overview`を読み、対応ガイドと必要な手順を選ぶ。毎回全ガイドを読み直す必須フローは設けない。

### ガイドの種類と内容

| 種類 | 例 | 内容 |
| --- | --- | --- |
| 全体説明 | `overview` | 接続先と保存先、操作群、利用範囲の取得、文書ID・版・状態、関連ガイドへの入口 |
| ツール別 | `tool.search_documents`、`tool.edit_document_draft` | 用途、前提、引数の入手元、入力・出力、作用、制限、失敗と対処 |
| 作業手順 | `workflow.search-and-cite`、`workflow.import-and-read`、`workflow.edit-and-commit`、`workflow.recover-operation` | 複数ツールの順番、前の結果から次へ渡す値、分岐判断に必要な状態、成功と中断条件 |

ツール別ガイドには次を必須とする。

- 使う場面と、対象外の形式・処理。
- 必要な権限、現在版・抽出完了などの前提、先に取得するIDやETag。
- HTTPとMCPの呼び出し形の違い。既存文書ツールの`arguments`ラッパーを省略しない。
- 引数・応答スキーマへの参照と、各フィールドの意味・単位・取得元。
- 最小の成功例と、競合・未設定・通信断などその操作に必要な失敗例。
- 保存、索引、外部送信、再実行等の副作用。該当しない操作も読み取り専用であることを明示。
- 再試行可否、保持するキー、再取得すべき版、次に参照するツールとガイド。

例示は合成資料と架空の認証情報を使う。実在の秘密情報を例に含めず、IDはfixtureの結果から束縛する。説明例を検証時に呼ぶ場合も、実環境のIDや資料へ置き換えない。

### HTTP API

利用ガイドAPIはgatewayに追加する。通常の接続例では18768番ポート側であり、ナレッジAPIの18766番ポートと区別する。gateway固有の閲覧接続・MCP操作まで説明できるため、ここをガイド提供の入口とする。

| メソッドとパス | 入力 | 応答 |
| --- | --- | --- |
| `GET /api/v1/tool-guides` | 任意の`kind`、`tool_name`、`cursor`、`limit` | 公開済みガイドのID・題名・要約・対応ツール・版・次のcursor |
| `GET /api/v1/tool-guides/{guide_id}` | 任意の`section`、`cursor`、`max_chars` | ガイドメタデータと本文、関連ガイド、スキーマ参照、取得範囲と続き |

`kind`と`tool_name`は明示した値の構造的な絞り込みに限定する。初期版に自然言語を分類する検索サービスは作らない。用途の選択は一覧の要約を読んだLLMが行う。

詳細応答は`schema_version`、`catalog_revision`、`guide_id`、`guide_revision`、`title`、`kind`、`tool_names`、`required_actions`、`sections`、`related_guides`、`schemas`、`schema_refs`、`next_cursor`を持つ。各sectionは安定したIDとMarkdown本文を持つ。応答上限で切れる場合は`next_cursor`と返却範囲を明示し、手順を無言で切り落とさない。

ツール別ガイドの`schemas`には公開契約から導出した入出力スキーマを含め、HTTPとMCPの引数形式を識別する。スキーマ用sectionから同じ認証経路で取得でき、参照先URLを別の資格情報で開く必要がない構成にする。`schema_refs`は契約と版の追跡に使い、説明取得の必須経路にはしない。

`max_chars`は返すMarkdown本文のUnicodeコードポイント数とする。数値上限とスキーマを含む応答バイト上限はP0で既存制限とEumenesの入力予算から定める。cursorはガイド版とsectionに結び付け、古い版の続きを新しい本文へ接続しない。版違いは構造化エラーと再取得先を返す。

未知のガイド・sectionは404、入力違反は422、古いcursorは409とする。エラーには安定したcodeと必要なガイドIDを含める。製品の業務エラーコードは既存のものを維持する。

### MCPと既存ホストAPI

MCPには同じ引数・内容を持つ次の2ツールを追加する。

```json
{"name":"list_tool_guides","arguments":{"kind":"workflow","limit":20}}
```

```json
{"name":"get_tool_guide","arguments":{"guide_id":"overview"}}
```

```json
{"name":"get_tool_guide","arguments":{"guide_id":"tool.edit_document_draft","section":"recovery"}}
```

この`arguments`はMCPの`tools/call`のフィールドである。既存の一部文書ツールが業務引数をさらに`arguments`へまとめる形式とは区別し、ガイド例では実際の登録スキーマに従う。

HTTP GET、MCP、既存`POST /host/tools/{name}`は一つのガイド読み出し処理を呼ぶ。MCPでは構造化結果を返し、互換性のため本文も読み取れる形にする。専用Resourceへの対応をEumenesへ要求しない。MCP Resourcesでの提供は後から同じ処理へ追加できるが、初期実装の必須条件にしない。

### 認証と機能情報

新しいGET APIは、既存の利用者別`mcp_token`をBearerとして検査し、read権限を要求する。`mcp.py`内の検証処理をMCP SDKに依存しない共通関数へ最小限切り出し、HTTPとMCPで同じ失効検査を使う。ホストAPIは既存の信頼するホストの資格情報と利用者対応を維持する。トークンをURL、ガイド本文、モデル引数へ渡さない。

ガイドは管理者が配布する公開操作の説明であり、利用者の文書内容や私有設定を含めない。read利用者もwrite操作の説明を読めるが、読むことで実行権限は増えない。登録されていること、利用者が実行できること、処理サービスが現在稼働していることを別々に扱う。現在の実行可否は`get_document_capabilities`と業務操作自身で確認する。

全ガイドの詳細取得を認証し、失効後の要求を拒否する。初期版は既存方針に合わせ`Cache-Control: no-store`とし、Eumenesの会話内で参照する版を`catalog_revision`で識別する。利用者をまたぐ認証応答の共有キャッシュは設けない。

API停止時も、gatewayで認証できれば同梱された説明は読める。業務操作の稼働状態が不明なら不明と返し、説明の取得成功を文書処理の成功として扱わない。

## 6 ガイドの正本と契約整合性

ガイドの正本は`src/docling_desk/resources/tool-guides/`に置く読み取り専用のmanifestとMarkdownにする。下書きDB、Wiki、利用者の文書、LLMによるその場の生成をガイドの正本にしない。利用者が入力した文書の命令をガイドへ取り込まない。

manifestにはガイドID、種類、対象ツール名、section、関連ガイド、必要action、公開状態を記録する。引数・応答の型は既存OpenAPIとMCP登録から参照・導出し、説明文に独立した型定義を増やさない。gatewayのガイドAPI契約は`contracts/tool-guides.openapi.json`へ追加し、業務APIのOpenAPIとは提供元を分ける。

追加ツールの登録、入出力スキーマ、対応ガイド、例の整合を検査する。既存の固定操作表とMCP登録を利用し、ガイドのためだけに業務実行を新しい汎用レジストリーへ移さない。必要な追加は説明メタデータと契約検査に限定する。

CIで、公開ツールのガイド欠落、存在しないツール・section・関連ガイドへの参照、入力例のスキーマ違反、必須出力の説明不足、配布資源の欠落を失敗にする。将来候補は計画書で管理し、未登録のツールを実行可能なガイドとして公開しない。

`catalog_revision`は説明・参照スキーマ・対応ツール集合を含む配布内容から決定する。本文だけ変更した場合も更新し、実行時に対応を推測しない。契約版が一致しない配布ではガイドAPIと追加操作のreadyを失敗にし、互換性のない説明を返さない。既存の無関係な画面まで停止する構成にはしない。

wheel・sdist・gatewayの実行環境へmanifest、Markdown、ガイドAPIスキーマを同梱する。チェックアウト直下のファイルがある場合だけ動く読み出しは避け、インストール済み資源を基準にする。

## 7 追加操作の実装方針

### ファイル取り込みとバイナリ

既存gatewayのJSON経路は2 MiBの入力上限を持つ。HTTP取り込みの上限50 MiBを、そのままbase64引数へ詰める方式は採用しない。大きなファイルはLLMの文脈を経由せず、Eumenesのホストから認証付きHTTP経路へ転送する。

P0でEumenesのMCP対応、利用者の伝達、ファイル転送と画像受信を確認する。既存の取り込みAPIへ直接転送できればその結果のsource・job参照をMCPで引き継ぐ。gateway経由が必要なら、ホストが転送したファイルを利用者・scope・用途・期限へ限定した一時IDとして受け付け、`import_document`と`replace_document_source`はそのIDを受け取る最小の受け渡しを追加する。モデルがサーバーの任意パスや取得URLを指定する契約にはしない。

一時受け渡しが必要な場合は、有効期限、再送時の再利用、実行中の保持、成功後と期限後の削除を既存の再送契約と合わせて確定する。再送キーと要求内容から同じ操作を確認できることを先に検証する。Eumenesのファイル参照を読めるという仮定だけで実装を進めない。

画像は認可済みの既存プレビューをMCPの画像コンテンツとして返す。上限に合わせた解像度と形式を定め、取得版とページ情報を同時に返す。大きな原本やCSVは、同じ認可を要する取得経路を返し、資格情報を含むURLを本文へ保存しない。

### 本文の範囲と表

独立APIが管理する既存の抽出成果物・親文脈・表構造を使用し、資料ごとの再OCRやLLMでの再解析を取得のたびに行わない。API・非公開processor・gatewayの既存責務に沿って取得入口を追加する。

範囲・表・画像の取得では、source・原本版・根拠版・要素IDの対応と認可を検証する。推測した要素IDを受け入れず、一覧やoutlineで得た参照を用いる。改版・再抽出後の古い参照は既存根拠と同様に拒否する。必要な構造が存在しない場合は、未準備・非対応を区別して返す。

### 保存と処理状態

処理開始は既存の永続ジョブへ登録し、短時間でjob参照を返す。MCP呼び出し中に抽出・索引完了まで無期限に待たない。ジョブ確認は既存状態を正本とし、別の進捗台帳を作らない。

原本登録・本文確定、FTS準備完了、意味索引準備完了を区別する。Embedding失敗時のFTSへの縮退と理由を維持する。`reindex_document`は保存済み抽出の再利用、`reextract_document`は抽出の再実行であることをガイドと応答で区別する。

既存編集のETag、ハッシュ、再送キー、7日間の結果照会を維持する。古い下書きの自動マージや、新しいキーでの無条件な再送はしない。PDF・Officeの原本をMarkdown編集で上書きしない。

## 10 設計判断と進め方

Descriptionだけを増やす方式は、操作間の依存・復旧手順を分量を抑えて伝えにくいため採用しない。全説明を毎回モデルへ注入する方式も、必要な部分だけ取得する本計画の方式へ置き換える。

MCP Resourcesだけの提供はEumenesの対応に依存するため、HTTP APIと通常のMCPツールを必須経路にする。実行時にLLMがガイドを生成する方式は、契約とのずれや権限説明の変動を避けるため採用しない。LLMは配布済みのガイドを読み、状況に応じた選択と説明を担当する。

担当外の不具合は証拠と影響を報告し、勝手に修正しない。最後に差分全体を確認し、個別の発話・対象・例へ依存する専用分岐、LLM判断の固定処理、秘密情報、無関係な変更が増えていないことを確認する。
