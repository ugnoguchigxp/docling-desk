# docling-desk 外部文書基盤の実装計画

docling-deskを、外部アプリからHTTP APIとMCPで利用できる文書・Markdown・RAG基盤へ拡張する。独立ナレッジAPIを正本とし、既存の登録・改版・認証・検索・ジョブ・閲覧を再利用する。Markdown下書き、競合を検出する編集、保存版の確定、添付管理、最小の見たまま編集画面を追加する。

2026年10月14日時点の計画。現状確認の対象コミットは `1b27e5ac2d2f66970286a02515a99d49d5688f76`。本書の作成では製品コードを変更していない。以下のAPI名・応答項目は実装予定の契約であり、既存APIとの整合を確認して確定する。

## 1 目的と担当範囲

最初の受入は、隔離した資料による「登録 → 検索と根拠取得 → MCPでMarkdown下書き作成 → 部分編集 → 人が見たまま編集で確認と修正 → 保存版確定 → 検索反映 → 引用から閲覧」とする。回答生成は呼び出し元が担当でき、docling-deskの回答生成APIを必須にしない。

| 担当 | 責務 |
| --- | --- |
| docling-desk | 文書の正本、原本、添付、保存版、下書き、抽出、検索、根拠、閲覧API、MCP、今回追加する最小編集画面 |
| Eumenes | 会話、編集と閲覧のArtifact、利用者認証との接続、ブログなどへの公開操作。今回は接続契約と例を渡す |
| Plate | 見たまま編集部品の第一候補。公開APIや保存形式は依存させない |
| LARM | サービスのホストと起動停止、LLM・Embedding資源。今回はdocling-desk側の運用境界を整える |

外部連携の保存先は `knowledge-api` のSQLiteと原本領域に限定する。既存デスクトップ画面・Wikiの `data/` は統合・移行しない。同じ文書をそこへ複製し、独立して編集する正本を作らない。既存画面から新しい編集入口へのリンクを追加する場合も、データ取得は独立API経由とする。

Eumenes・LARM本体、外部ブログサービス、媒体別変換、投稿、本番配備は対象外。リアルタイム共同編集、自動マージ、OAuth基盤の新設、全体リファクタリングも初期実装に含めない。新しい依存ライブラリは編集・構文解析に必要なものだけに限定する。

## 2 利用者が決定した仕様

| 項目 | 決定 |
| --- | --- |
| 人向け編集画面 | docling-desk内に最小の画面を追加し、見たまま編集を含める |
| 未対応のMarkdown記法 | 原文を保護して表示し、必要時にソース編集へ切り替える。対応外の記法を黙って消さない |
| 改版後の引用と埋め込み閲覧 | 既存方針を維持し、古い引用は拒否して最新版の再検索へ案内する |
| 下書きの単位 | 一文書に複数の下書きを作れる。下書きIDを指定して人とAIが同じ下書きを編集する |

検索対象は確定した保存版だけとし、下書きは検索に出さない。AIによる下書き作成・編集・確定は認証済みの書き込み接続から利用でき、人の承認を必須とする新しい業務規則は追加しない。編集画面では利用者が明示して保存版を確定する。

現状の機能はソース確認によるもの。既存試験の存在と、今回その試験が成功したことは区別する。既存試験の実行は実装開始時のベースラインで行う。

| 閲覧仲介 | [gateway.py](../src/docling_desk/viewer/gateway.py)、[viewer-embedding.md](viewer-embedding.md)。接続コード3分、文書単位セッション5分、資料・権限変更で失効 | 閲覧セッションを編集権限へ転用しない。編集用の短期セッションを同じ仲介で追加 |
| 表示と位置 | [DocumentViewer.tsx](../frontend/src/viewer/DocumentViewer.tsx)、[viewer-embedding.schema.json](../contracts/viewer-embedding.schema.json)。原本版と根拠版、page・slide・sheet・documentの位置 | 共通viewerを使用。Markdownの引用位置は現状document単位なので、原文範囲を検証して開ける位置契約を追加 |

既存の原本取得は明示的な過去版指定を持つ。過去版検索・原本取得を維持しつつ、通常の根拠と埋め込みviewerに過去版閲覧を新設しない。

## 4 正本と状態の契約

### 文書と下書き

確定したMarkdownは、既存 `sources`・`revisions` と不変の `original.md` を正本とする。下書きは同じSQLite内の追加テーブルで管理し、公開前の編集状態として位置付ける。別DBやエディタJSONを新しい正本にしない。

下書きは `draft_id`、対象文書IDまたは新規作成先のscope、基準の `source_revision` と文書ETag、本文、メタデータ、添付参照、更新連番、本文SHA-256、作成者・最終更新者、状態を持つ。既存文書から作る下書きはその文書の現在の認可を毎回引き継ぎ、新規下書きは保存したscopeを毎回検査する。作成者だけの私有物にはせず、同じ範囲のread・writeに従う。

下書き更新は下書きETagを必須にする。確定時は下書きETagと基準の文書ETagを両方検査し、読み取り後の再検査も含めてトランザクション内で確定する。新規文書の確定では、まだ対象文書が存在しないことを検証する。一つの下書きから複数の保存版を作らない。確定済み下書きは変更せず、再編集は保存版から新しい下書きを作る。

他者の編集が入った場合、未保存の入力を勝手に破棄せず、競合と最新状態の再取得方法を示す。自動的な上書き、推測による統合、古い下書きの基準版だけを付け替える操作はしない。

### 保存結果と検索反映

| 状態 | 契約 |
| --- | --- |
| 下書き保存済み | SQLiteへの本文・メタデータ・添付参照の保存が成功。抽出・Embedding・検索公開を行わない |
| 保存版確定済み | 不変の原本、版、ハッシュ、下書きとの対応、操作結果、検索反映要求が永続化された |
| 検索反映待ち | 確定保存は成功している。ジョブ待機・処理休止・容量上限でまだ反映されていない |
| 全文検索反映完了 | 現在の原本版に対応する根拠版とFTSが公開された |
| 意味検索反映完了 | 現在のProvider識別・profile・次元数と互換性のあるEmbeddingが公開された |
| 検索反映失敗 | 確定本文は保持。失敗段階・エラーコード・再試行可否を返す。FTS成功後のEmbedding失敗ではFTSを保持する |

確定応答には文書ID、保存版、文書ETag、本文ハッシュ、下書きIDと確定した下書き版、操作結果識別子、検索反映状態、追跡可能なジョブIDを含める。原本版と根拠版を混同しない。本文ハッシュはUTF-8原文から求め、原本のSHA-256と一致させる。

保存版と索引処理を分けるため、確定処理は永続ジョブまたは同等の既存永続状態を同じトランザクションで残す。キュー上限は実行・受付の調整に使い、本文確定をロールバックする理由にしない。新しい汎用ジョブ基盤は作らず、既存ジョブの待機・受付を調整する。

旧版は最新版の検索状態として見せない。改版直後は既存どおり旧版を通常検索から外し、最新版の反映待ちを明示する。処理が失敗しても、最新版であるかのように旧本文を返さない。

### メタデータと権限範囲

初期版は既存metadataのtitle・languageなどを編集し、frontmatterとは別に管理する。APIタイトルの変更でMarkdown本文を書き換えない。メタデータ更新も文書ETagと冪等性キーを必要とし、文書のgenerationを更新する。本文が同一なら不要な抽出やEmbeddingを起動しない。確定時のメタデータを版に結び付けて記録し、保存後の管理情報変更と区別する。

権限範囲の変更は明示操作として扱い、変更前と変更後の両scopeへのwriteを検査する。利用者が持たない範囲へ移動できない。更新・削除・scope変更時は、保存済み検索、下書き、添付、viewer、editorを現在の文書認可で検査する。scope変更中のジョブには版・runに加えて権限範囲の変更を検出する条件を適用し、旧scopeの索引やベクトルを公開しない。

クライアントや利用者の権限設定変更と、文書scope変更は別の試験にする。前者の既存失効検査を、新しい編集経路にも適用する。

## 5 HTTPとMCPの公開契約

HTTPを公開業務操作の入口とし、MCPとブラウザー仲介は同じ操作を呼ぶ。MCPからDB・原本領域へ直接保存しない。以下のルート名は契約確定時に既存OpenAPIの命名へ合わせる。

仲介は許可した業務操作から固定のAPIルートへ接続し、モデルが指定した任意のパスやURLを転送しない。任意ファイルパスの読書き、シェル実行、任意URLへの認証付きアクセスを公開しない。文書本文・検索結果・添付・エディタ内の文字列はデータとして扱い、その中の命令で利用者、scope、接続先、ツール権限を変更しない。

| 操作 | HTTPの追加または再利用案 | MCPの案 | 主な条件 |
| --- | --- | --- | --- |
| 利用範囲 | `GET /api/v1/scopes` | 既存 `list_document_scopes` を共通応答へ接続 | 接続由来のread・writeと許可scopeを返す |
| 文書一覧 | `GET /api/v1/sources` | `list_documents` | 認可を適用してからページング。件数にも範囲外を含めない |
| 文書情報と本文 | 既存source取得、`GET /api/v1/sources/{id}/body` | `get_document` | 原本版・ETag・ハッシュを指定。Markdown原文とOfficeなどの抽出本文を区別 |
| 検索と根拠 | 既存search・context | 既存search・contextツール | retrieval所有者・scope・原本版・根拠版を再確認 |
| Markdown作成 | `POST /api/v1/markdown-sources` | `create_markdown_document` | 冪等性キー必須。既存保存版登録の業務操作を利用 |
| メタデータ更新 | `PATCH /api/v1/sources/{id}/metadata` | `update_document_metadata` | 文書ETag、冪等性キー。本文は不変 |
| 下書き作成 | `POST /api/v1/drafts` | `create_document_draft` | 冪等性キー。既存文書では基準版とETag必須 |
| 下書き取得と一覧 | `GET /api/v1/drafts/{id}`、認可された一覧 | `get_document_draft`、`list_document_drafts` | 下書き本文、版、ETag、基準版、保存状態を返す |
| 全文更新 | `PUT /api/v1/drafts/{id}` | `update_document_draft` | 下書きETag、冪等性キー。Markdown文字列が本文 |
| 部分編集 | `PATCH /api/v1/drafts/{id}` | `edit_document_draft` | 下書きETag、基準ハッシュ、検証可能な編集指定、冪等性キー |
| 保存版確定 | `POST /api/v1/drafts/{id}/commit` | `commit_document_draft` | 下書きETagと基準文書ETag、冪等性キー |
| 操作結果照会 | 操作種別・対象・冪等性キーを受ける専用照会 | `get_document_operation` | 接続のclient・subjectから操作を特定し、現在の認可を再検査 |
| 添付登録と参照 | 下書き・文書に属するattachments登録・一覧・内容取得 | `add_document_attachment`、`get_document_attachment` | 対象ETag、登録の冪等性、scope、バイト数、ハッシュを検査 |
| 検索反映状態と再試行 | source状態、既存jobs・retry・reindex | `get_document_job`、必要な再試行ツール | 保存成功と処理失敗を区別。現在版にだけ再試行を許可 |
| 閲覧 | 既存viewer | 既存閲覧と接続承認ツール | 確定した原本版・根拠版・位置を必須にする |

原本のPDF・OfficeをMarkdownに書き換える操作は提供しない。その抽出本文は根拠として読めるが、編集する場合は出典を持つ別のMarkdown文書・下書きを明示的に作成する。

要求・応答サイズ、ページング、添付上限は契約に含める。JSONは既存の2 MiB制限を基準にし、エスケープを含む実際のサイズで検査する。HTTP添付は既存原本の50 MiB上限を基準とする。MCPの初期添付送信はbase64のJSON制限内に限定し、大きい添付はHTTP登録後の安定IDを使う。切り詰めて成功として返さない。分割アップロード基盤は必要性が確認された場合の追加項目とする。

### 部分編集

サーバーは文章の意味を判断しない。呼び出し元LLMまたは編集部品が対象を選び、次のいずれかで指定する。

- 範囲編集は、基準本文に対する0始まりUTF-8バイト範囲 `[start, end)`、期待する原文、置換文字列を受ける。文字の途中、範囲外、原文不一致を拒否する。挿入は空範囲で指定する。
- 原文一致編集は、空でない期待原文と置換文字列を受け、基準本文に厳密一致が一つだけ存在する場合に限り適用する。0件・複数件では拒否する。正規表現や曖昧一致は受けない。
- 複数編集は全て同じ基準本文に対して検証する。範囲の重複や順序が曖昧な同位置挿入を拒否し、全件成功時だけ一度の更新として適用する。

ETag不一致は412、必須条件の欠落は428、対象不一致・複数一致・冪等性衝突は識別できる409、引数・UTF-8境界の不正は422を基本とする。認可失敗時は本文や他者の操作結果を返さない。MCPでも構造化した同じエラーコードと再試行可否を返す。

### 再送と追跡

既存idempotencyテーブルを拡張し、本文の更新・確定・操作結果を同じトランザクションで記録する。成功済みの同じ要求は、その要求が使った古いETagでも同じ結果を返す。再送判定の前にも認証・現在の認可は必ず行う。異なる利用者の結果や削除・失効後の本文は返さない。

冪等性キーの保持は初期版では既存の7日間を維持する。再起動で消さない。キーには操作種別と対象を含め、異なる要求なら409。期間外の結果不明を成功・未実行と推測せず、新しいキーで自動再送しない。保存版と追跡記録から確認する手順を用意する。

追跡記録にはclient・actor・操作ID・基準文書版・基準下書き版・結果版・前後のハッシュを保存する。本文や資格情報を通常ログへ出さず、HTTPとMCPの両経路から同じ保存結果を確認できるようにする。HTTPとMCPで同じ操作として再送する場合は、同じclient・actor・操作種別へ正規化する。

## 6 Markdown原文と添付の保持

Markdown本文は有効なUTF-8の原文として保存する。取得した本文を変更せず保存した場合、BOM、改行、末尾改行、frontmatter、空白、コードフェンス、Mermaid、数式、参照リンク、HTML・MDX、媒体固有ブロックを含むバイト列とハッシュを保持する。不正UTF-8を代替文字へ黙って置き換えない。

下書き本文の空文字は許可する。確定した空文書も失敗した抽出と区別し、検索候補なし・意味索引対象なしの状態を表す。新規作成時のUTF-8や改行規則は明示し、既存本文をその規則で一括正規化しない。

添付は不変のID・SHA-256・媒体型・サイズ・表示名と、下書きまたは文書との関連を持つ。指定された文書と添付の所属が一致することと、その文書への認可を両方検査する。参照の案は `knowledge-attachment:<attachment_id>` とし、viewerとeditorが認可された取得先へ解決する。本文には一時blob URL、署名付きURL、Bearer付きURLを埋め込まない。

確定版に添付IDの一覧を記録する。差し替えは新しい添付IDを発行し、旧版で参照したファイルを上書きしない。下書きだけの添付は下書きに結び付け、確定時に文書との対応を永続化する。資料削除では参照を即時失効し、既存削除ジョブで原本・下書き・添付・索引を片付ける。保持中の保存版が参照する添付を容量整理で消さない。

HTML・MDX・コードは保存しても実行しない。プレビューは原文とは別の派生表示であり、既存の表示安全化を再利用できる範囲を確認して補う。外部画像を自動取得せず、添付画像は認可された取得経路だけから表示する。

## 7 最小の見たまま編集画面

独立API専用の編集入口をfrontendに追加し、既存Wikiの編集・保存先と混同しない名称と導線にする。文書と下書きの選択、見たまま編集、ソース編集への切替、添付、下書き保存、保存版確定、検索状態、競合と再取得を提供する。

最初の見たまま編集対象は段落、見出し、強調、箇条書き、リンクとする。frontmatter、数式、Mermaid、コード、表、HTML・MDX、未知の媒体ブロックは原文を保持した保護ブロックとし、ソース編集で変更できる。リンク定義など別の位置の原文に依存する構文は、対応を確認できない限り保護対象にする。安全に描画できないブロックは文字列として表示する。

原文文字列を編集バッファの基準とし、エディタJSONは表示・操作の派生状態に限定する。保存時に全文をJSONから再生成しない。編集可能な構文の原文位置を持ち、変更した範囲だけを原文へ適用する方式を先に試作する。未変更部分はバイトで保持し、編集した範囲の記法が変わる場合は差分として確認できるようにする。位置対応が曖昧になった操作は適用せず、ソース編集へ案内する。

[PlateのMarkdown公式資料](https://platejs.org/docs/markdown)はJSONとMarkdownの相互変換、個別ノードの変換、独自要素のMDX化を説明している。既存原文のバイト保持を確認した証拠としては扱わない。無編集の往復、混在記法、日本語・絵文字・改行、段落分割・結合、貼付け、取り消し・やり直しを試し、採用可否を判断する。Reactとの互換性・必要依存・ライセンスは選定する固定版で確認する。

既存閲覧セッションはreadのみで、編集へ昇格させない。編集用に短期・利用者・scope・対象文書または下書き・actionを限定した接続を追加し、既存接続コード承認を再利用する。新規下書き作成用の接続も作成先scopeを限定する。モデル引数やURL中の利用者IDは認証に使わず、認証されたMCPまたは信頼するホスト接続がコードを承認する。

ブラウザーへ長期Bearerや署名鍵を渡さず、短期編集セッションはメモリー内で保持する。閲覧・編集双方で失効と対象の認可を通信ごとに検査し、Host・Origin・CSRF相当の要求検査、CSP、第三者埋め込み時のsandboxを試験する。URLが開いたことを認証成功としない。初期版は既存gatewayと同じ単一プロセスで動かし、再起動でセッションが失効しても保存済み下書きは残る。

自動保存は下書きだけを対象とし、更新を直列化して応答されたETagを次の要求へ渡す。同じ下書きを人とAIが編集すると、古いETagの更新は停止する。「保存版確定済み」の後に「全文検索反映待ち」「意味検索未設定」などを別に表示する。画面を閉じても確定保存や実行中ジョブを取り消さない。

Plateで原文保持を満たせない場合は、失敗した操作と原文差分を示して実装方針を見直す。全文再シリアライズで通すことや、ソース編集だけを見たまま編集の完了として扱うことはしない。編集部品の代替はAPI契約を変えずに検討し、目的・範囲が変わる場合だけ利用者へ判断を求める。

## 8 検索と引用からの閲覧

確定Markdownを既存Extractor境界へ渡し、原本から検索用の派生本文・チャンク・根拠版を作る。Doclingによる抽出結果を原本へ逆流させない。Markdown抽出が落とす記法や空本文は、原文保持と検索対象化を別に検証する。

検索結果では原本版・根拠版・context IDを保持する。状態取得では現在の保存版、その版のFTS・semantic準備状態、根拠版、失敗・待機理由を返す。Embedding未設定・接続失敗・互換性不一致のときは既存の全文検索への縮退と `effective_mode`・`degraded_reasons` を明示する。

Markdownの引用位置は原文SHA-256とUTF-8範囲を持つ契約を追加する。抽出チャンクから原文位置を確実に対応付けられる部分だけ付与し、重複や対応不明では推測しない。対応不明の場合は文書先頭から開き、その状態を返す。PDF・Officeのページ・スライド・シート位置は既存契約を維持する。

文書改版・削除・scope変更・再抽出で原本版または根拠版が変わると、古い通常引用を拒否する。gateway、API、viewer資産取得の各段階で検査し、表示済み画面も失効通知後に本文を除く。添付の取得にも同じ検査を適用する。検索結果の表示名や位置だけを最新版へ差し替えない。

遅延した処理結果には、文書の現在版、処理run、削除状態、権限範囲の整合を公開前に検査する。更新と削除によるsuperseded状態を再利用し、scope変更時にも同等の防止を加える。本文保存済み・FTS成功・Embedding失敗を、ジョブcompletedだけで一括成功と扱わない。

## 9 LARM管理下の運用境界

| 単位 | 起動と停止 | 永続性とヘルス |
| --- | --- | --- |
| APIとSQLite Writer | 常駐可能。単一Writer。停止時は受付終了、状態記録、リース解放 | 原本・版・下書き・操作結果・ジョブを保持。liveとreadyを既存入口で提供 |
| API内のジョブ実行部 | 保存受付と独立して処理を休止できる最小の管理境界を追加 | 待機ジョブを保持。休止中をreadyのcapabilitiesで明示 |
| Python processor | 重い抽出・Office描画・OCR。ブラウザーの終了とは独立に管理 | 非公開ポート、処理token、原本領域だけを共有。SQLiteやactor鍵を渡さない |
| gatewayとMCPとeditor | APIから独立して起動可能。初期版は一つのgatewayプロセス | 短期セッションは再起動で失効。live・readyとAPI接続状態を追加 |
| 原本領域とstate領域 | サービス停止と領域削除を分離 | SQLite、原本、添付の整合したバックアップと復元を用意。通常停止でvolumeを削除しない |

processor停止中も、保存済み本文・下書きの読書き・Markdown確定は利用できる。Officeの描画などprocessorが必要な操作は利用不可を明示する。Compose起動依存と `capabilities.source_management` を、本文保存能力・抽出能力・閲覧能力へ分けて確認する。

既存の通常停止は実行中ジョブをfailed/interruptedにし、明示retryを基本とする。異常終了したローカル処理はリース期限後の回復を維持する。外部課金や受領不明の操作は、通常のローカル再試行と分け、無条件に再送しない。LARMからの休止・再開は管理用境界に限定し、文章編集MCPへ任意プロセス操作を公開しない。

Embeddingは管理者の保存設定からURL・token・profile・次元数を解決する。モデル名を製品コードに固定しない。接続先、profile、モデル版、次元数、処理仕様が変われば互換性のないベクトルを除外し、現在の設定で再索引する。LARMから得る情報をこの設定へ接続するために必要な項目を文書化する。

LARMのサービス登録、起動停止API、Secret供給、profile照会、Embeddingの実HTTP仕様は正式契約を確認してから接続する。現段階では既存Provider契約と起動コマンド・管理境界までを整え、LARM側のAPIパスや設定キーを仮定した実装は作らない。

## 11 検証計画

検証は部分 → 結合 → 通しの順とする。fixtureは外部課金設定を読み込まず、決定的なProviderを使う。実HTTP、実MCP transport、実ブラウザーはモック呼び出しだけで代替しない。

### 部分試験

| 試験 | 成功条件 |
| --- | --- |
| 下書きと文書の競合 | 同じ下書きETagの二更新、異なる下書きから同じ文書版の二確定で一方だけ成功。本文と確定版を上書きしない |
| 部分編集 | 原文0件・複数件、UTF-8境界、重複範囲、古いハッシュ、無効な一編集で、本文とETagが全く変わらない |
| 原文保持 | BOM、CRLFとLF、frontmatter、コード、Mermaid、数式、参照リンク、画像、HTML・MDX、未知ブロック、日本語・絵文字を含むfixtureの無編集往復がバイト一致 |
| 見たまま編集 | 対応構文の挿入・削除・分割・結合・貼付け・undoで、編集外の原文を保持。未対応部分を変換・実行しない |
| 冪等性 | 同一要求の再送は同じIDsとハッシュ。異なる要求は409。7日保持と期限外の不明状態を検査 |
| 添付 | 安定ID、ハッシュ、旧版参照、所属文書不一致と権限外文書の拒否、削除、サイズ制限、一時URLを正本へ書き込まない |
| 保存と処理の分離 | 下書き自動保存でExtractor・Embedding要求0件。processor停止・キュー満杯・Embedding失敗でも確定本文を保持 |
| 認証 | readだけの接続、scope外、偽actor、モデル引数のuser_id・actions・scope偽装、期限切れ、設定失効を拒否 |
| ジョブ競合 | 更新・削除・scope変更の途中で旧runが完了しても、最新版の索引・状態・添付を復活させない |

### APIとMCPと画面の結合試験

同じ永続DB・原本領域を使い、HTTPで作った文書をMCPで読み、MCPで作った下書きをHTTPとブラウザーで編集する。HTTPとMCPで同じactor・操作に正規化した再送も確認する。読み取り専用ユーザーと編集ユーザー、scope外ユーザーを別々に用意する。

応答喪失は「保存後、クライアントが結果を受け取る前」に注入し、同じキーの再送・照会で確認する。実プロセス停止は原本書込み前後、DB確定前後、下書き確定直後、索引公開直前に注入する。DB、原本ハッシュ、操作記録、ジョブ、Provider要求数を独立して照合し、孤立ファイルの回復・整理も確認する。テスト中に対象コードを編集して結果を無効にしない。

ブラウザーでは接続承認前の取得拒否、read接続から編集への昇格拒否、編集の自動保存競合、期限切れ・gateway再起動後の再接続、添付表示、保護ブロック、検索状態を検証する。長期資格情報がURL・本文・localStorage・通常ログへ出ないことも確認する。

Markdownの検索結果から原文範囲へ移動する試験と、PDF・Officeの既存位置の回帰を分ける。scope変更と資格失効では古い検索・根拠・閲覧・編集・添付の全経路を試す。

### 最初の通し受入

1. 空の専用state・artifactsと隔離scopeにPDF・Office・Markdownの合成資料を登録する。
2. HTTPとMCPで検索し、retrievalと根拠本文・原本版・根拠版を取得する。
3. MCPで根拠を参照する新規Markdown下書きを作り、厳密一致の部分編集を適用する。
4. 人向け画面から同じ下書きを開き、見たまま編集で修正し、未対応記法を保持する。
5. 古いMCP更新を拒否し、最新の下書きを再取得して保存版を確定する。応答喪失後の結果照会と再送も行う。
6. 確定本文とハッシュを取得し、全文検索反映完了を確認する。Embeddingなしと、fixture Embeddingありの両条件を試す。
7. 引用の文書・版・位置で埋め込みviewerを開き、認証承認後に原文と添付を確認する。
8. 改版・削除・scope変更、処理中の停止・再起動を追加し、古い参照の拒否と最新版の保持を確認する。

### 実行入口と記録

既存入口は `knowledge-api` の `bun test`、`bun run typecheck`、`bun run lint`、`bun run contract:check`、`bun run test:integration`、`bun run test:docker`。Pythonは `.venv/bin/python -m pytest` とRuff、frontendはpnpmのtypecheck・lint・test・buildを利用する。実装時に追加するMCP・編集画面・通し試験の入口は、既存QAスクリプトとPlaywrightへ組み込み、単一の受入手順から実行可能にする。

通常Python試験では `DOCLING_ENV_FILE=/dev/null` を設定する。合成試験のProvider URLと資格情報を明示し、既存環境の外部モデルへ送信しない。Dockerが利用できない場合などの省略は、失敗と分けて理由・代替確認・残る試験を記録する。

実装の完了には部分試験、実HTTP/MCP結合試験、実ブラウザーを含む隔離fixture通し受入、公開契約一致、必要な関連回帰を必須とする。実LLM・LARMは正式契約と環境がある範囲で実施し、未実施なら完了報告に理由と追加手順を残す。fixture成功を実LLM・LARM成功へ読み替えない。

検証記録の予定先は `qa/external-document-platform/verification.md` と結果JSON。対象コミット、入力manifestとハッシュ、環境、実行入口、成功・失敗・省略、DBと原本の照合結果を保存する。本文と秘密情報は記録しない。

## 12 接続手順と外部側の残作業

実装完了時には、[knowledge-api.md](knowledge-api.md)、[viewer-embedding.md](viewer-embedding.md)、OpenAPI、viewerとeditorのschema、`integrations/` の設定例を更新する。外部連携の一覧・本文・下書き・編集・確定・状態・結果確認の契約を一つの手順で説明する。

HTTPの接続例は、サーバー側でclient Bearerと短期actor JWTを付け、本文取得 → 下書き作成 → ETag付き編集 → 確定 → 状態確認 → 結果照会を示す。JWTのaudは既存の `docling-desk-api`、署名は既存HS256・kidを使用する。資格情報はSecretまたは権限制限ファイルから読み、例に実値を含めない。

MCPの例は、既存の `public_url + /mcp/` に利用者別Bearerで接続し、一覧 → 検索 → 根拠 → 下書き → 部分編集 → 結果取得 → 確定 → 閲覧接続承認を示す。利用者IDや権限をツール引数で申告させない。読み取り専用は閲覧用APIクライアント、編集ユーザーは許可された編集用APIクライアントへ対応付ける。HTTPとMCPでの操作追跡・再送に使うclientとactorの対応を説明する。

Eumenesへ渡すのは、資格情報を含まない文書参照、原本版、根拠版、引用位置、下書きID、編集結果と操作ID、viewer・editorの入口とホスト通信契約。iframeのOriginや開閉を認証・ジョブ取消として扱わず、postMessageの送信元・形式・対象参照を検査する例を用意する。編集承認の接続コードも利用者・対象・actionへ結び付ける。

| 外部側 | 残る作業 |
