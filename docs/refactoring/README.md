## 目的と守る範囲

利用者が資料一覧、Wiki、原本閲覧、検索、翻訳、解説、図編集を移動しても、現在地と操作方法を見失わない状態にする。実装側では、同じ役割の処理を既存の共通機構へ寄せ、機能固有の契約を追いやすくする。

操作の統一は、外枠、操作の優先順位、用語、通知、戻り先、キーボード操作を対象にする。原本文書の内部レイアウトは変更対象にしない。PlateやExcalidrawの固有操作は、その機能で必要な差として残す。

次の契約を全工程で維持する。

- 原本バイト、資料ID、Wiki記事ID、既存の版、保存済み翻訳・解説、公開済み出典の対応を保持する。
- 通常画面、外部API、埋め込みビューアーの認可と信頼境界を保つ。CSP、iframe sandbox、ツール権限、通信先・容量・時間の制限を緩めない。
- サーバーの処理状態を正本とし、画面に別の業務状態管理を作らない。未保存の入力や選択状態は画面が管理する。
- 外部要求の受付が不明な場合の自動再送禁止、取消後・削除後・権限失効後の公開禁止を保つ。
- 公開HTTP/MCPのURL、入力・出力・エラー、ETag、冪等性の契約を維持する。追加診断情報は既存契約と認可を壊さない形で設計する。
- 意味、関連性、意図の判断はLLMに委ね、コードは入出力、実行、状態、契約、権限を担う。形式判定や数値上限など外部仕様上の制約はコードで強制する。

対象外は、新しい業務機能、全体のフレームワーク刷新、PythonとTypeScriptのDB統合、マイクロサービス化、認証方式の変更、利用者データの清掃、公開・配布の実行。新しい共通部品は実際の利用先と削減できる重複を示してから追加する。

保存形式の変更が必要になった場合は、実装前に移行・旧版読出し・復元・切り戻しまで同じ作業票に含める。実装開始時に未コミット変更があれば、初期化したり、上書きして整理したりしない。

## 工程と依存関係

R19は、最初の検証整備をR19a、最後の配布候補確認をR19bとして実施する。同じ1件の前半・後半であり、20件を増やした扱いにはしない。

| 工程 | 実施順と対象 | 終了条件 |
| --- | --- | --- |
| G0 基準と検証 | R19a。R20の配布物一覧も採取 | 固定コピー、同じ入力・設定、現行の検証結果を保存。図編集3シナリオが意図した末尾の検査まで到達 |
| G1 通信と状態 | R09 → R04 → R10 → R11 → R08 | HTTPの情報を失わず、表示と取得の責務が分かれる。機能の終了状態を誤って統一しない |
| G2 画面の責務 | R06 → R07 | Wiki・検索・資料操作を個別に変更でき、外見・URL・保存動作を維持 |
| G3 操作の統一 | R01 → R02 → R03 → R05 | 共通の外枠・表現・操作規則が主要画面に適用され、原本表示と埋め込みを保持 |
| G4 保存と実行 | R12 → R14 → R13。R15もこの工程で実施 | 故障時・終了時・競合時の契約を実証。R13は設計確認を通るまで実装に進まない |
| G5 意味判断と利用開始 | R16 → R18 | 補足調査の意味判断と送信制約を分離。機能別の設定不足から復旧できる |
| G6 性能と配布 | R17 → R20の配布候補確認 | 機能を保ったまま読込を改善。最終配布物と依存・資産の台帳が一致 |
| G7 通しと再評価 | R19b | 同一版で通し・配布・性能・復旧・操作評価を完了し、実績から再採点 |

各作業の詳細な前提は実装計画に記載する。R15とR16はR19a後に独立して進められるが、担当を分ける場合も共有ファイルと評価用の配布物を同時に変更しない。人員・担当者名・日程は未割当であり、同時実行を前提に日数を短く見積もらない。

初回の変更単位は **R19a → R09 → R04** とする。最初から外枠・CSS・取得・保存を一つの差分で変更しない。G2までは構造と振る舞いの維持を確認し、G3で意図した見た目の変更を行う。

## 作業の区切りと担当

各R項目を独立してレビューできる変更単位にする。R13・R14・R19は契約確認、実装、検証をさらに分ける。コード移動と挙動修正は、同じ作業の中でも差分を区別する。新しいファイル名は配置案であり、同じ責務の既存実装が見つかればそちらを使う。

画面担当はR01〜R11・R17、Python担当はR12〜R14・R16・R18、外部API担当はR15、配布・検証担当はR19・R20を担当範囲とする。1人が複数の役割を持ってよい。保存と認可の変更では、実装時の検証とは別に、入力・出力・保存実体から確認する手順を設ける。同じ人の確認を独立した第三者検証とは呼ばない。

S・M・Lは変更範囲であり所要日数ではない。日程はG0の基準採取、担当割当、R13の設計確認後に決める。ライセンスの確認、実モデル評価、新規Linux環境の準備は、コード量から所要時間を決められない依存作業として残す。

## 進捗と停止の条件

実装着手後は各作業票の「状態」「対象版」「検証証拠」「残作業」を更新する。未着手、進行中、検証待ち、完了、阻害ありを使い、変更量や経過時間では完了にしない。異なる対象版の成功結果を一つの完了判定に混ぜない。

同じ目的の試行が3ラウンドに達したとき、または根拠の増えない同一失敗、検証中の対象変更、計画からの逸脱を認めたときは、次の編集・再実行の前に目的・証拠・残作業・未解決仮説を確認する。継続か方針変更か、変わった条件と次の一手をこの会話で短く報告する。正常に進む長時間処理は経過時間だけで停止しない。新しい根拠がなければ試行を止め、差分と続行条件を残す。

担当外の失敗は原因と影響の調査までとし、便乗修正や期待値の引下げを行わない。データ消失、認可逸脱、原本改変、取消後の公開が再現した場合は、その変更の依存作業を止める。

## 完了と再評価

20件すべてで実装、必要な契約更新、受入検証、切り戻し手順を満たす。採用しない共通化や最適化が生じた場合は、実際の利用先や測定結果で不要と判断した理由を記載し、黙って完了数に含めない。

画面の一体感は、同じ代表作業の完了、戻り先、キーボード操作、エラー復旧と、改修前後の操作観測で確認する。利用者数や検証回数だけを効果として扱わない。[検証と再評価](verification-plan.md)の条件を満たすまでは、技術点・将来性の上昇を実績として報告しない。

既存の品質改善計画との整合を取る管理目標は、全30技術項目を評価できる状態と、実績による80点超えを目指すこと。ただし20件の構造改善完了と、80点超えの達成は別に判定する。未確認や点数不足が残れば、理由と必要な検証を報告し、達成済みにしない。将来性は利用効果・導入・定着などの実観測が得られた項目だけを更新する。
