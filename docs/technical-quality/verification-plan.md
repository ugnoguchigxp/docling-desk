# 技術品質改善の検証と再評価計画

この文書は、[実装計画](implementation-plan.md)の完了を実際の証拠で判断するための条件を定めます。目標台帳は計画上の仮定です。試験成功、未確認、実施条件外、別作業での報告を区別して記録し、新しい実績台帳で80点超えを判断します。

## 試験環境と証拠の保存

G0でコミット、未コミット差分、Doclingの実行版、モデルrevision、ロックファイル、Python・Bun・Node・pnpm・ブラウザー・OS・CPU・メモリを固定します。Linuxではイメージ識別値とvolume構成も記録します。各試験は同じ対象版で実行し、後続の変更があれば影響する試験を再実行します。

通常の試験は合成文書と許可済みの固定fixtureを用い、専用の保存領域、fake provider、テスト用資格情報を使います。外部OCR・embedding・回答・Web取得の本番設定を引き継がず、利用者の`data`、`.knowledge-api`、保存済みWikiを変更しません。現在の画面fixture準備は未作成時にローカル`data`をコピーするため、CI用には合成fixtureだけで初期化する入口をQ08で用意します。

1試験につき、対象版、入力manifest、コマンド、終了値、開始・終了時刻、環境、HTTP応答、DB・成果物の観測、外部要求数、制限を記録します。本文やキーをログへ残す必要はありません。合成データのID・ハッシュ・件数・エラーコードで追跡できる形にします。保存先の案は`qa/technical-quality/<固定版>/`です。

今回の計画作成時の確認結果は[確認記録](planning-baseline.json)にあります。これだけで以下の試験全体が成功したとは扱いません。

## 主要経路と境界条件

6形式はTXT、Markdown、PDF、DOCX、XLSX、PPTXです。正常な小文書だけでなく、上限付近、空・破損・形式不一致、部分抽出、非ASCII名、表、画像、Office描画不可を含めます。文字・表・ページ／シート／スライドの対応を検査し、原本のハッシュが変化しないことを確認します。

現在のローカル設定には1ファイル50 MiB、100ページ、空き領域2 GiB、Office展開250 MiB・10,000項目などの条件があります。API側の別上限は契約から取得し、同じ値だと仮定しません。各上限の直前・一致・直後と、未申告サイズで拒否が効くか試します。

| 対象 | 必須ケース | 合格条件 |
| --- | --- | --- |
| 登録・版管理 | 再送、キュー満杯、同時登録、途中の資格失効、更新失敗 | 1回だけ確定し、権限・状態・再送結果が一致。成功版を契約どおり保持 |
| 検索・親文脈 | 短い日本語、全角、重複語、同文の別出典、空条件、scope、更新・削除 | 許可範囲を順位計算前に適用。別出典を失わず、古い版を現在の根拠にしない |
| Wiki | 複数記事の一括取り込み、同パス更新、manifest、UTF-8、境界パス、本文削除 | 正本・索引・リンク・言語対応が一致。失敗時に半端な取り込みを残さない |
| 意味検索 | 未設定、次元・モデル版変更、索引途中、同時要求、429、取消 | 旧ベクトルを混ぜず、待機・失敗を明示。要求数と間隔を守る |
| OCR | native text、画像、回転0・90・180・270度、crop、受領不明、壊れたcache | 本文と座標・出典が契約どおり。不要な送信・無断再送・旧runからの更新なし |
| 回答・解説・翻訳 | 不正provider応答、時間切れ、停止無視、資料内の命令、設定変更 | 検証済み応答だけを保存し、原本と権限を保ち、停止後に公開しない |
| 印刷 | 現在・全体・指定範囲、重複・不正範囲、抽出だけ成功、悪意あるHTML、取消 | 指定ページと内容が一致。能動コンテンツや外部要求なし。古い読み込みが復帰しない |
| 権限・乱用 | 他scope、失効、write-only、read-only、slow body、9並行検索、大きい応答 | 範囲外の本文・件数・出典を返さず、枠を解放し、通常処理へ復帰できる |

全文検索と意味検索の関連度、OCRの文字認識精度は、技術的な契約成立と区別して測ります。必要な精度は用途別にG0で固定し、実データと人手の正解がない場合は未確認として報告します。

## 停止と再起動を試す境界

各行をHTTPだけで判断せず、別プロセスからDB・成果物とfake providerの要求台帳を観測します。境界を注入できない場合は、対象箇所にテスト用の注入点を設けます。通常実行で注入設定を有効にしません。

| 終了・失敗の注入位置 | 再起動・再試行後に成立する条件 |
| --- | --- |
| 原本保存前後と登録DB確定前後 | 孤立物の扱いが明示され、重複登録や欠けた資料を公開しない |
| 抽出後と索引公開前後 | 未完了版を検索しない。成功版の切り替えは契約どおり一括 |
| lease取得後、期限切れ後、旧workerの遅延応答 | 旧所有者が新しいrunや削除済み資料を変更しない |
| 取消受付後にabortを無視するproviderが完了 | 索引・回答を公開せず、中断状態を維持 |
| 同じ失敗ジョブへ2つのretry | 1つだけ受付。DBとジョブ・資料状態が一致 |
| OCR送信意思の保存後、POST直前、応答紛失、poll中、cache保存後 | 成否不明を明示し、自動再送なし。明示再送は一度だけ消費 |
| embedding通信中と待機期限保存前後 | 再起動でも最小間隔・保留と同一設定の直列化を維持 |
| Wikiの複数記事更新中と削除中 | 一括確定またはロールバック。旧検索結果から削除本文を取得しない |
| ファイル・DB書き込みで容量不足、読み取り専用、破損cache | 保存済み正本を保全。失敗原因と安全な復旧方法を提示 |
| バックアップと復元、版更新とロールバック | 正本・出典・状態が一致。外部要求の無断再送や削除資料の復活なし |

## 性能予算の案

以下は**G0で測定前に確定する提案値**です。現状の実測値でも、合格済みの値でもありません。対象外の規模を保証しません。利用規模を変更する場合は、その理由と評価範囲を記録します。

環境案はLinux CPU 4コア・メモリ16 GiB、単一API所有者と処理worker、GPUなし。ローカル画面は対象Mac環境でも別に測ります。データ案は100・1,000文書、計10,000検索チャンク、Wiki100記事、PDF最大100ページ、1024次元の意味索引。APIが受け付ける8192次元は別の境界負荷条件として測り、同じ性能を保証しません。

| 測る項目 | 提案する予算 | 測定条件 |
| --- | --- | --- |
| 全文検索 | p95 300 ms以内 | 索引作成済み、10,000チャンク。同期を含む利用者の待ち時間を測る |
| キャッシュ済みHybrid | p95 2秒以内 | 同規模、同じモデル設定。検索範囲・削除・更新条件も含める |
| 親文脈取得 | p95 500 ms以内 | UI既定4,000トークン。API上限16,000は別測定 |
| API 8同時検索 | 全文p95 1秒以内、9件目を制御 | slot占有、時間切れ、取消後の解放と復帰を確認 |
| 一覧・Wiki表示・画面遷移 | 温状態1秒、冷状態2秒をp95目標 | LAN／ローカル、配布bundle、固定ブラウザー |
| サービス全体のメモリ | 宣言した通常負荷でRSS合計8 GiB以内 | API、Python、変換子プロセスを合算。最大ページ・高次元も別に記録 |
| 外部要求とキャッシュ | 変更なし再索引は追加embedding 0、同条件再取得は0 | 有効cache時。期限・モデル設定変更・cache削除は別契約 |
| 保存容量と保持 | 上限と保持期間をG0で数値化 | 原本／正本、再生成物、完了ジョブを分け、整理後の再利用を検査 |

変換と印刷は形式・ページ数に依存するため、G0で固定した代表入力の初回測定から利用上の上限時間を決め、以後の回帰閾値を記録します。時間上限が未定のまま`performance.budget`を合格にしません。Azureの通信・最低15秒待機・Retry-Afterをローカル2秒予算へ混ぜず、利用者の総待ち時間も別途示します。

暖機後の30回以上を初期測定案とし、冷状態・更新時・負荷時は別系列にします。1回の外れ値を消さず、p95と最大値、失敗率を残します。基準の1.2倍を回帰調査の目安とし、CI環境のばらつきや確定予算の超過を併せて判断します。回数と比率は計画上の運用値であり、測定だけで性能を保証するものではありません。

## 再評価の計算と判定

評価基準はrubric 1.1.0、technical、balanced、deep。10分野の重みは設計10、正確性15、安全性15、信頼性10、保守性10、共通部品5、テスト10、依存と配布10、性能7、運用と操作8です。各分野内の3項目は同じ重みです。

計算は、各項目の値を0〜4で決めてから、`25 × Σ（分野重み ÷ 3 × 項目値）÷ 100`で行います。目標構成は4が9項目、3が21項目で83.75、表示83.8です。すべてが3なら75。4が未実証の項目を3へ下げた場合の減少は、設計・信頼性・テストの各項目が約0.833点、正確性・安全性が各1.25点、共通部品が約0.417点です。修正1件につき一定点を加算する方法は使いません。

現在のExpected台帳と計算結果は[目標台帳](target-review.json)・[試算結果](target-score-summary.json)に保存します。この計算の証拠充足率100%は「全ての仮定が成立した場合」の台帳上の値であり、現在の実証率ではありません。正式スコアはnullです。

再評価では別の`re-evaluated-review.json`を作り、実際の根拠ID、値、根拠の強さ、反証、4のanchor support、制限を記入します。reviewスキルの`score_review.py`で検証・計算し、目標台帳は保持します。元の評価との比較では同じ基準と適用範囲を使い、新機能による範囲拡大と、共通して評価できる項目の変化を分けます。

80点超えの完了条件は、正式スコアの丸め前の値が80を超え、全30項目に実績の根拠があり、適用除外なし、確認済みCritical・High問題なし、重大な疑いの未調査なしであることです。通常の採点ポリシーの上限制約も適用します。小さな制限を残す場合は影響・利用条件・担当を記録します。

未確認が残る場合は正式評価を出しません。証拠充足率70%以上で必須分野が揃った場合だけ、上下限付きの暫定値を扱えます。その値を80点超えの達成としません。数値の条件を満たしても、安全性・正確性・復旧に重大な問題が残る場合は実装計画へ戻します。
