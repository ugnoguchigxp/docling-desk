# 構成と変更の境界

Pythonのインポート可能なコードは `src/docling_desk` に集約しています。`app.py` は起動時の処理、ミドルウェア、ルーターの接続を行います。

| ディレクトリ | 責務 |
| --- | --- |
| `api` | HTTPの入力・応答、アップロード、ライブラリー、閲覧、翻訳・解説・診断のルート |
| `documents` | 原本の検証、抽出、RAG、表、OCR連携、保存済み資料の操作 |
| `preview` | PDF・Office・HTMLの表示とキャッシュ |
| `knowledge` | Wiki、検索、SQLite索引、外部サービス用の処理worker |
| `translation` / `explanation` | Provider契約、状態、実行管理、表示への適用 |
| `wiki_batch` | 既存Wikiの移行と再開可能なバッチ |
| `viewer` | 外部ナレッジAPIのビューアーゲートウェイ、任意のMCP接続 |
| `operations` | モデルの取得・検証、バックアップ、保持、配布検証 |
| `evaluation` / `development` | チェックアウト内で使う評価・合成サンプル作成 |
| `resources` | 読み取り専用の静的画面、モデルmanifest、補助スクリプト、保持ポリシー |

HTTPルートは `api/dependencies.py` の資料参照を共有します。ルートから `app.py` をインポートしません。アプリのデータとモデル設定は `config` を参照します。低水準のOCR証拠は `documents/evidence.py`、プレビューのハッシュは `preview/hashing.py` に置き、OCR/RAGや書き出し/描画の循環を避けています。

Provider生成と任意のMCP登録には遅延importがあります。外部接続を実行するProviderと契約・状態管理は分離します。配置を整えるためだけの新しい抽象層は追加しません。

## 資源と状態

`config.RESOURCES` はインストールされた資源です。原本、モデル実体、キャッシュ、`.env` はここへ書き込みません。開発用インストールでは既存チェックアウトの状態を使い、通常インストールでは利用者の状態ディレクトリを使います。環境変数で個別の保存先を指定できます。

画面のURLと資料ID、DB、原本・抽出成果物の形式は構成移行の前後で共通です。旧Pythonモジュール名の互換ファイルはリポジトリ直下に増やさず、起動コマンドを新しい名前へ更新します。

## 公開・配布

`data/` の既存原本と大量のQA成果物は、ファイルをローカルに保持したままGitの管理対象から外しました。公開準備のため、親リポジトリのローカル履歴を現在のコードを含む初期コミット1件に作り直しています。旧履歴と変更前の作業ツリーはプロジェクト外の非公開バックアップに退避しています。Doclingサブモジュールは公開upstreamの固定コミットを維持します。リモートの旧履歴はこのローカル操作では変更されません。

合成fixtureと評価corpus、再実行に必要な検証スクリプトは残します。Reactの生成物はGitに追加せず、CI・Docker・wheel生成の前にビルドします。ライブの画面では旧ハッシュを保持し、wheelとsdistでは現在のHTMLから参照する資産だけを含めます。

開発環境の清掃で、Git管理外の投入文書5件とその成果物・検索DB（計940ファイル）、検証画像、一時キャッシュを削除しました。現在の利用者データは空です。Git管理済みのCI・E2E・ユニットテストと合成fixtureは維持し、CIで使う保存済み合成解説もGit管理しています。

## 検証

- `DOCLING_ENV_FILE=/dev/null .venv/bin/python -m pytest tests -q`: クラウド設定を読み込まないPython検証。
- `.venv/bin/python -m ruff check .`: 配置・import・未定義参照。
- `.venv/bin/python scripts/verify_package.py`: sdistからwheelを作り、別ディレクトリで資源、起動、取り込み、検索、削除、書き込み先を確認。
- frontendとknowledge-apiのテスト・型確認、合成ブラウザー検証。

Docker daemon、実Azure、実資料のすべての表示品質は別の検証条件です。実行していない検証を合格扱いにしません。

## コンテンツ保存の分離（2026年10月5日）

資料の原本とWiki本文は `data/content/`、抽出結果は `data/derived/`、SQLiteと資料ジョブは `data/runtime/`、サムネイルは `data/cache/` に分離する。パスの組み立ては `storage.py` を共有する。画面の資料ID・記事ID・URLと、表示上の分類は維持する。

Wikiの正本はMarkdown・CSVと `content/manifests/wiki.json`。ファイルを書き終えた後にmanifestを一括で置き換え、SQLiteへ検索用の状態を反映する。manifest公開前の失敗は記事を変更しない。公開後にDBの更新が失敗した場合は、次の読み取りまたは起動でファイルから索引を復元する。原文のfrontmatterもファイルに保持し、索引には本文と管理情報を分離して保存する。

SQLiteを含む `runtime/` はBlob同期対象にしない。Azureの接続・同期・競合解決は別の実装対象で、この変更はローカルの保存契約を整える。編集用のWikiバッチワークスペースは従来の規約を維持し、`sync`でコンテンツ正本へ公開する。

検証は `tests/test_content_layout.py` で、原本バイトとIDの保持、移行の再実行、SQLiteなしからのWiki復元、複数記事の公開失敗、manifest公開後のDB失敗、コピー・削除、バックアップ復元を確認する。既存のWiki・資料・プレビュー・翻訳・解説のPythonテストと配布検証も実行する。実Azure接続は含めない。競合する移行先やリンク経由の保存先は上書きせず、エラーとして停止する。
