# 文書ビューアー連携の実装・検証記録

検証日：2026年10月4日。計画の初期版（段階0–5）を実装した。導入手順は `docs/viewer-embedding.md`、再現手順は `reproduce.md`、参照・通信契約は `contracts/viewer-embedding.schema.json` にある。

実装後のコードレビューで見つかった問題は修正し、追加の回帰テストと既存Braveプロファイルで確認した。最新の修正と検証は `review.md` と `review.json` を参照する。本書の接続検証と一括ブラウザー試験は実装時点の記録として保持する。

## 実装結果

共通のDocumentViewerを通常画面と埋め込み専用入口から使用する。資料取得先とホスト通信をインスタンス単位に分離し、埋め込みでは一覧・アップロード・Wiki・生成処理を呼ばない。PDF、PPTX、XLSX、DOCX、Markdown、TXTの原本または本文、抽出表、構造、RAGデータを表示する。

確定した処理試行を資料・原本版・根拠版に対応付け、独立ナレッジAPIの閲覧要求から解決する。閲覧仲介、実際のStreamable HTTP MCP、Open WebUIネイティブToolを実装した。引用にはembed_url、明示的な閲覧要求にはRich UIを使う。Open WebUI本体の変更は不要である。

ブラウザーにはAPIの資格情報を渡さない。接続コードを現在の利用者のToolで承認し、対象資料と版だけを取得できる5分の閲覧セッションを発行する。再読込とコピーしたチャットでは新しい承認が必要になる。

## 環境と資料

- Open WebUI 0.11.4-slim。Docker image digestはcompose.yamlで固定。標準のallow-scripts allow-downloads sandboxを使用した。
- 最終のブラウザー検証はBrave 154.1.96.60。Chromiumエンジンの報告値は154.0.8037.93。途中までChromeでも検証し、利用者の指定後はBraveに切り替えた。最後の操作確認は、すでに開いているBraveプロファイルの拡張接続を使用した。
- API、文書処理、閲覧仲介、固定応答モデルを隔離したポートで起動。通常のdata/、既存Open WebUIのアカウントと設定には変更を加えていない。
- 6形式の連携資料は合成データ。PDF/PPTX/XLSXは保存済み変換fixture、DOCX/Markdownは実際の変換、TXTはアップロードとworker処理を使用。全Office形式の新規変換品質を検証したものではない。
- 原本と実装ファイルのSHA-256はverification.jsonに保存した。資格情報と生の閲覧セッションは記録していない。

通常画面の最終一括実行で残った1件は、翻訳範囲チェックボックスを外す自動操作が状態変更を検出できなかったもの。翻訳要求の検証に進む前に停止した。途中のChrome実行では同じ試験が成功している。最後に既存Braveプロファイルで、範囲を外したときの拒否、スライド1の再選択、再翻訳指定、間隔0での実行、訳文表示まで確認した。証拠はexisting-profile-results.jsonとexisting-brave-translation.png。一括実行全件成功とは扱わない。

Wordの保存済みQuick Look fixtureは、表示完了を確認してキーボードで印刷を開く試験にした。実際に変換したDOCXのマウス操作は別途確認した。PDFメニュー試験も非同期の原本・操作欄の準備を確認してから操作する。通常画面のPDFでタブを往復すると位置が変わる問題は、非表示時の寸法処理を修正し、回帰試験で確認した。

## 初期版の運用条件

閲覧仲介は1プロセスで実行する。接続コードは3分、セッションは5分。履歴に保持するのは資料参照で、再接続は現在の利用者で承認する。表示中も15秒ごとに権限と版を確認する。提供済みの内容を回収できるとは扱わない。

導入前の抽出結果は確定した表示試行の対応がないため、必要な資料を再抽出して使用する。埋め込み内の翻訳・解説生成、原文保存、印刷、セル範囲や座標の強調表示、MCP Apps、標準Artifactsへの直接登録は追加対応である。通常画面の既存機能は維持した。

一つのiframeに一つのビューアーを配置する。同じReactルートへの複数配置は既存DOM IDの分離が必要になる。実際の本番Open WebUIと実モデルへの導入は設定例と手順書で行う。この検証では外部LLMのTool選択品質を評価していない。
