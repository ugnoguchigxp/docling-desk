# Wiki・資料横断検索のレビューと修正

2026年10月4日。対象は、直前に追加したMarkdown Wiki、資料とWikiの全文・意味検索、根拠取得、Azure embeddingの待ち時間管理、および既存閲覧画面との接続。ソースを確認し、問題を再現するテストを追加して修正し、再レビューと既存操作の確認を行った。

## 修正した指摘

| 優先度 | 問題と影響 | 修正・検証 |
| --- | --- | --- |
| P1 | 大きい節の全文を検索断片ごとに複製し、DBと検索時のメモリー使用量が膨らむ | 親文脈を共有保存し、取得時だけ読む。約120KB・31断片の検証でDBは4,337,664バイトから737,280バイトに減少。旧DBを移行しても断片ID・保存済み検索IDを保持するテストを追加 |
| P1 | 存在しない範囲でも意味検索をキューへ入れ、空の範囲指定が全件検索に広がる | 開始前と通信待機中に対象を確認し、空の範囲値は拒否。存在しない対象がジョブを作らないことを確認 |
| P2 | 検索IDが全文検索と意味検索で別扱いになり、同じIDの条件変更で追加処理が作られる | 検索方法をまたいでIDを照合し、条件変更を拒否 |
| P2 | 1資料の不正なJSONLが健全な資料の検索まで止める | 行の型、本文、参照、ページ、親ID、重複IDを確認。不正資料を索引から除き、健全な資料が検索できるテストを追加 |
| P2 | 一覧・状態取得が不要な本文やベクトル全体を読み込む | 本文を含まない一覧取得、要求ハッシュだけのベクトル取得、ハッシュだけの索引状態取得を使用。リンク先の見出しは必要な記事だけ解析 |
| P2 | 完了後の検索結果とコピー可能な根拠が、記事の更新・削除後も画面に残る | 完了結果もGETで再照合し、結果の変更に対応する根拠表示を解除。削除後の結果消去と、検索POSTが1回のみであることをブラウザーで確認 |
| P2 | 閉じた画面に遅い応答が入り、履歴操作後に取り込み完了が画面を戻す。利用できなくなった範囲が残る | 非同期応答を開始時の画面に結び付け、削除対象のIDを固定。利用できない範囲を表示上もリセット。遅延応答・履歴移動・モード切り替えの操作テストを追加 |
| P2 | 検索URLのページ指定が言語変更のたびに再適用され、手動移動が戻る | ページ指定を範囲内に補正し、原本の準備後に一度だけ適用。PDF・XLSXで手動移動後のタブ・言語切り替えを確認 |
| P2 | 一時的なSQLite障害で唯一のワーカーが終了し、所有権を失った処理や古い接続設定のジョブが通信を続ける | キュー取得失敗から復帰。更新は所有権を条件にし、送信直前にも中止を確認。ジョブの接続設定を固定し、変更後の自動再送を拒否するテストを追加 |
| P2 | 200応答の形式不正でRetry-Afterを落とす。同時書き込みで異なる次元が混ざる | エラーにも待ち時間を保持し、トランザクション内で次元を再確認。応答の数値・添字を検証し、正規化と類似度計算の桁あふれを避ける |
| P2 | 不正なAzure URL・次元設定がWiki全体を利用不能にする | 設定エラーを状態画面に返し、Wikiと全文検索を継続。3種類の不正設定で確認 |
| P2 | 閲覧機能の分離後、言語選択が内部表示に伝わらず、印刷画面を閉じたときのフォーカスが戻らない | 言語状態を渡し、画面の終了後にメニューへフォーカスを戻す。既存の操作テストで確認 |
| P2 | Wiki本文・検索文・キャッシュを含む実行時DBがGitの対象になる | `/data/knowledge/`を除外。実データを削除しない |

## 検証結果

- Python一式：340件成功、既存の環境条件による1件skip。そのうちWiki・検索は30件成功。
- React単体：11ファイル・34件成功。
- ブラウザー：Wiki11件と既存操作38件、合計49件成功。
- TypeScript、ESLint、対象PythonのRuff、差分の空白検査：成功。
- 本番画面のビルドと静的配信への書き出し：成功。

並行する変更でビルドが切り替わる影響を避けるため、最後のブラウザー検証はビルドの固定コピーを使用した。初回のブラウザー実行ではテストの要素指定にも誤りがあり、実際の要素名と閉じるボタンの位置を確認して修正した。既存の印刷画面の終了後フォーカスの失敗は実装を修正し、3形式の再確認と全体49件の再実行で成功した。成功件数はそれぞれ検証時点の作業ツリー・固定ビルドに対する結果である。

旧DBの移行、保存容量、範囲検証、次元の競合、中止、所有権、接続設定変更、一時的なDB障害、設定エラーについて追加したテストは `tests/test_local_knowledge.py`、画面の再照合・遅延応答・範囲・原本位置は `frontend/e2e/wiki.spec.ts` にある。

現時点で、このレビュー範囲に未解決の重大な指摘はない。Azureの実リソースへの接続は未設定のため、実際のデプロイと契約上限による動作は未検証。通信の形式・待ち時間・失敗・中止は固定した応答で検証した。旧DBで解放した領域は再利用されるが、物理的なファイルサイズが即座に縮むとは限らない。

調査支援ツールの利用：今回のレビューで `context_compile` 1回、`compile_eval` 1回。初期指示の再取得や別Codexタスクへのメッセージ送信は行っていない。

ローカル反映：8765番のサーバーの所有プロジェクトと、資料変換・翻訳・解説・検索キューが稼働していないことを確認。SQLiteのバックアップを取って再起動し、Wiki一覧、索引状態、全文検索、保存済み検索の取得、画面配信が成功した。検索対象101断片、Wiki0記事、Azure未設定。実データへテスト記事は取り込んでいない。
