## 発見した問題と修正

| 対象 | 修正前に再現した問題 | 修正後 |
|---|---|---|
| 同時検索数 | 本文を読み終える前に並行9要求が制限を通り、全件200になった | 本文読み取り前に枠を確保。8件200、1件429。失敗時も枠を解放 |
| 出典の重複除去 | 同じ文章を持つ2資料の一方の出典・親文脈が消えた | 同じ資料・版・親文脈内の同じ検索本文だけを重複除去 |
| 短語検索 | 全角の「ＡＩ」を「AI」で検索できず、Unicodeの大小文字でも取りこぼした | 許可範囲内の候補を正規化して照合。走査中に時間上限も確認 |
| 検索語の上限 | FTS候補抽出と順位計算で重複除去・32語上限の位置が違い、後ろの有効語が消えた | 同じ検索語生成関数を両方で使用。再レビュー時の回帰も修正 |
| 登録再送 | キューが3件で満杯だと、同じIdempotency-Keyの再送まで429になった | 再送結果を確認してから永続キューへ新規登録を判定。multipart同時読み取りは3件に制限 |
| 削除済み資料の再送 | 削除後の登録再送が202を返した | 現在の資料状態と権限を確認して404 |
| 資格情報の失効 | multipart読み取り中に資格情報を失効させても、再送結果が202で返った | 本文読み取り後にも利用者・資格情報・書き込み権限を確認し401 |
| 大きいEmbedding | 対応範囲内の8192次元を16件まとめると2 MiBの応答上限を超え、処理が失敗した | 次元数に応じてバッチを減らす。17件を8・8・1件に分けて完了 |
| 回答の時間切れ | Providerの期限切れが `processing_failed` になった | `answer_timeout` として区別 |
| 再試行状態 | 再試行受付後も資料がfailedのままで、検索が処理待ちを表示しなかった | 資料・ジョブの段階を待機／索引処理へ戻す |
| 停止後の抽出 | abortを無視して遅れて返るExtractorがFTSを公開し、ジョブを完了できた | 戻った結果の公開前にも停止を確認。索引を公開せずinterrupted |
| 停止後の生成 | abortを無視して返るProviderが回答を保存・完了できた | 生成後・完了前に停止と期限を再確認。回答本文を保存しない |
| 書き込み専用権限 | write権限だけのクライアントが抽出ジョブをretryできなかった | retryはwrite、状態取得はreadとして別々に判定。対象資料のscope確認は継続 |
| 同時再試行 | JSON本文を待つ2要求が同じfailed状態を読み、両方202になった | トランザクション内で最新の権限とジョブを再取得。202と409に分かれる |
| Python設定取得 | OCR profileのJSON本文がクエリ引数として扱われ、実HTTPの登録が422になった | リクエストモデルをFastAPIが解決できる位置へ移し、JSONを正しく受理 |
| Docker構築 | 新しい処理パッケージがビルド対象から除外され、COPYで失敗した | 対象パッケージだけを明示的に含め、生成物と秘密設定の除外は維持 |

回答Providerの戻り値も共通スキーマで検証し、API契約は本文を省略できるretryの実際の挙動と一致させた。検証用起動は実環境のEmbedding・回答・Azure OCR接続設定を引き継がず、ローカル処理へ固定した。HTTP検証が失敗したときは、資格情報や本文を出力せずAPIのエラーコードを記録する。

再現したAPIの不具合は、修正前に失敗するテストを追加して修正後の成功を確認した。API全体を読み直し、修正後の認可、同時実行枠の解放、キューの上限、再送、旧版の参照、削除、停止後の公開可否を再確認した。
